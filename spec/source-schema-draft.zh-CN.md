# source（来源/溯源）· Schema 草案 v0

> 状态：**草案 v0.3，7 类已全部精雕定稿**。
> 定位：全局溯源机制（主文档第 4 节）。**图内自带来源副本**（每张图携带它引用的 sources），表达元素通过 `sourceIds` 引用图内 sources。
> 核心价值：**表达必须可溯源** —— 图上每个点都能指到"你凭什么这么说"的原始材料。这是案图的核心优势，每种图都要能做到。
> 原则：引用而非复制（图内表存一份、多对多用 id）；受控枚举 + 可选专属字段；**地基稳定优先（结构化定位），再谈功能扩展**。

## 0. 已定决策（发起人拍板，2025-09）

1. **定位字段走路线乙**（type 专属结构化字段，可校验、可跳转、可反查原始材料）——地基稳定，之后才好开发；
2. **type 每一类精心设计**，逐个精雕，不赶进度；
3. **sources 存放 = 方案 B：图内自带来源副本**。每张图携带它引用的 sources 表，单图自洽、可独立渲染、便于分享；将来若出现"一案件多图共享大量来源、需人工统一维护"场景，可能再升级为案件级全局表（方案 C，记为将来路径）。

→ 方案 B 的好处：单图文件独立可用；引擎无需跨文件寻址；来源由 agent 生成时顺手复制，冗余成本由机器承担。

## 1. source 需要回答的三个问题

设计任何字段前，先定 source 实体要支撑的三件事：

1. **这是什么**（给用户看的名称/类型）—— `name`、`type`
2. **它精确在哪**（溯源定位：页码/条号/案号）—— 结构化，在 `loc`（见 §3）
3. **原貌长什么样**（可选摘录，点开即见）—— `quote`

> 注：早期草案在通用层设过 `fileRef`/`url` 指向原始材料——**已废弃**。指向原始材料是定位职责，一律归各类型的 `loc`（卷内类 → `loc.file`，web → `loc.url`，statute/case 用标准寻址），避免与 loc 重复。

## 2. 通用字段草案

```jsonc
{
  "id": "s-1",              // ✅ 必填，全图唯一
  "type": "contract",       // ✅ 必填，受控枚举（见 §4）
  "name": "借款合同",        // ✅ 必填，显示名
  "title": "编号 XY-2023-001", // ❌ 可选：材料自身的编号/标题（与 name 区分：name=人话，title=原文名）
  "loc": { … },             // 定位字段（type 专属，见 §3/§4）——"指向原始材料"在这里
  "quote": "…原文摘录…"      // ❌ 可选：一小段原文，点开即见，不必翻材料
}
```

## 3. 定位字段：已定路线乙（type 专属结构化定位字段）

✅ 发起人已拍板：**结构化定位，地基稳定优先**。

原则：每种 source.type 配一组**标准定位字段**（可校验、可跳转、可反查原始材料）。定位字段**按 type 逐个精雕**（见 §4 的"待精雕"清单），先给出方向示例：

```jsonc
// statute（法条）→ 定位到具体条文（条号为数字，见 §4.2 定稿）
{ "type": "statute",
  "loc": { "lawName": "中华人民共和国民法典", "article": 585, "version": "2020修正" } }

// case（判例）→ 定位到具体裁判文书
{ "type": "case",
  "loc": { "caseNo": "（2024）京01民终1234号", "court": "北京市第一中级人民法院" } }

// document / contract / evidence → 定位到文件内位置
{ "type": "document",
  "loc": { "file": "借款合同.pdf", "page": 3 } }
```

> 统一约定：定位字段一律放 `loc` 对象内；`loc` 的具体字段按 type 精雕，见 §4。

## 4. type 枚举 + 字段一览（7 类已定，字段为 v0 草案）

**发起人决定：每一类都精心设计。** 以下为 7 类的字段一览；每类仍可逐个精雕调整。

### 4.0 通用字段（所有 type 共有）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 图内唯一，供 `sourceIds` 引用 |
| `type` | ✅ | 下表 7 类之一（受控枚举） |
| `name` | ✅ | 人话名（图上显示用，如"借款合同"） |
| `title` | ❌ | 材料自身的编号/原文标题（与 name 区分） |
| `quote` | ❌ | 原文摘录一小段（点开即见） |

> 通用层**没有**"指向原始材料"的字段——那是 `loc` 的职责（卷内类 → loc.file，web → loc.url）。

### 4.1 各类型的 loc 定位字段（type 专属）

| type | 是什么 | loc 必填字段 | loc 可选字段 | 定位逻辑 |
|---|---|---|---|---|
| `statute` | 法条/规范 | `lawName` 法规名、`article` 条号(数字)、`version` 版本 | — | 法规+条+版本 → 具体条文（已精雕，见 §4.2） |
| `case` | 判例/裁判文书 | `caseNo` 案号(标准整串)、`court` 法院 | meta：`level` 审级、`docType` 文书类型 | 案号+法院 → 唯一判例（已精雕，见 §4.3） |
| `contract` | 合同/协议 | `file` 原始文件、`clause` 条款号(数字) | `page` 页码 | 文件内条款/页（已精雕，见 §4.4） |
| `evidence` | 诉讼证据 | loc：`file` 原始文件 | loc：`page`；meta：`evidenceNo` 证据目录名、`party` 举证方（均可选） | 文件+（可选）证据编号/举证方（已精雕，见 §4.5） |
| `document` | 其他卷内文书 | `file` 原始文件 | `page` 页码 | 通用卷内定位（已精雕，见 §4.6） |
| `web` | 案外在线引用 | loc：`url`、`accessedAt` 访问日期 | loc：`platform`、`query` | 网址+时间固定（已精雕，见 §4.7） |
| `other` | 兜底 | — | `note` 自由说明 | 装不下时用（已精雕，见 §4.8） |

> 设计要点：
> - `statute`/`case` 的 loc **没有 file**——法条、判例用标准库寻址（法规名+条号 / 案号+法院），不需"文件+页"；
> - `contract`/`evidence`/`document` 是卷内材料，必须"文件+页"定位；
> - `web` 特殊在 `accessedAt`（访问日期）——网页会变，必须时间固定（证据固定）；`snapshot` 快照可选；
> - type 看"来源在当前案子里的角色"，不看获取途径：在线公示若作为证据提交 → `evidence`；仅案外引用 → `web`。

### 4.2 精雕定稿：statute（法条）——首个样板类型

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| 定位粒度 | 只到**条**（不细分款/项） |
| 条号格式 | **数字**（如 `585`），不用汉字"第五百八十五条" |
| 版本 | **需要** `version`（如 `"2020修正"`）——法条会修订，版本错则引用废 |
| name 与 loc | **方案乙**：`name` = 自由业务叫法（如"违约金条款依据"）；`loc` 负责精确寻址 |
| 条文内容 | **方案 C**：`quote` 存**摘录**、**限字数**、**不强制**（可选） |

```jsonc
{ "id": "s-2", "type": "statute",
  "name": "违约金条款依据",                       // 业务叫法，自由
  "loc": { "lawName": "中华人民共和国民法典",       // 权威全称
           "article": 585,                       // 数字条号
           "version": "2020修正" },              // 版本/时效
  "quote": "当事人可以约定一方违约时应当根据违约情况向对方支付一定数额的违约金…"  // 摘录，限字数，可选
}
```

**quote 通用规则（适用于所有 type，statute 首例确立）**：摘录而非全文、限字数（建议 ≤200 字，可调）、不强制。

> 注：`lawName` 用权威全称（"中华人民共和国民法典"）还是简称（"民法典"）——留待校验层讨论，schema 暂不强制。

### 4.3 精雕定稿：case（判例/裁判文书）

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| 案号 | **标准格式整串存**（如 `（2024）京01民终1234号`），不拆字段 |
| 法院 | **必填** `court` |
| 审级/文书类型 | **需要标注**，放 `meta`（审级：一审/二审/再审…；文书类型：受控枚举 判决/裁定/调解/决定/通知） |
| 渠道字段 | **不要**（砍掉）——不记录文书来源渠道 |
| 全文可查性 | 不保证（文书上网范围有限）→ `quote` 摘录**对 case 尤其重要**，沿用通用规则 |

```jsonc
{ "id": "s-4", "type": "case",
  "name": "某借款纠纷上诉案",                     // 业务叫法，自由
  "loc": { "caseNo": "（2024）京01民终1234号",   // 标准案号，整串
           "court": "北京市第一中级人民法院" },   // 必填
  "meta": { "level": "二审", "docType": "判决书" },  // 审级 + 文书类型（受控枚举）
  "quote": "…判决要旨摘录…"                      // 可选，≤200字
}
```

### 4.4 精雕定稿：contract（合同/协议）

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| 定位粒度 | `clause` 条款号用**数字**（如 `3`），不做款/项细分 |
| file | 指向**原始文件**（合同原件/扫描件），非文本转述版 |
| 合同双方 | **不存**——甲乙方属于 relationship 图内容，source 不重复 |
| 争议标注 | **不要** |

```jsonc
{ "id": "s-1", "type": "contract",
  "name": "借款合同",                              // 业务叫法
  "loc": { "file": "借款合同.pdf",                 // 原始文件
           "clause": 3,                            // 数字条款号
           "page": 2 },                            // 可选：页
  "quote": "…条款摘录…"                            // 可选，≤200字
}
```

### 4.5 精雕定稿：evidence（诉讼证据）

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| 证据编号 | 实务目录名："证据1"/"证据3"（保留原貌，不转数字）；**可选** |
| 证明目的 | **不收**——由 fact 事件的 `sourceIds` 衔接表达（论证属图内容，不冻结在来源里；证据常证多事，多对多归事件侧） |
| 举证方 | `party`（原告/被告/第三人）；**可选** |
| 证据种类 | **不要**（不做民诉法八类枚举） |

> **2026-09 修订（真实案例验证）**：`evidenceNo` 与 `party` 由**必填改为可选**。
> 原因：从判决书提取时常常拿不到——判决书多写"根据视频显示""结合诊断证明"，**不载明证据编号与举证方**（见 `examples/fact/elevator-smoking-case.zh-CN.json`，4 个 evidence 的这两字段均只能填"判决书未载明"）。填写它们需要额外材料（证据目录）。

```jsonc
{ "id": "s-5", "type": "evidence",
  "name": "银行转账流水",                          // 业务叫法
  "loc": { "file": "流水.pdf",                     // 原始文件
           "page": 1 },                            // 可选
  "meta": { "evidenceNo": "证据3",                 // 可选：实务目录名
            "party": "原告" },                     // 可选：举证方
  "quote": "…流水摘录…"                            // 可选
}
```

> evidence 与 document 的边界：document = "卷里有个文件"；evidence = "该文件被作为证据提交"，多了证据编号与举证方的程序身份。
> 证明目的不存于 evidence——它是论证（随诉讼策略变），论证归属图的事件引用侧，不是来源的客观属性。

### 4.6 精雕定稿：document（其他卷内文书）

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| 段落定位 | **不要** `para`——引用文书到"文件+页"即可 |
| 文书分类 | **不要** `docKind`——不分类，什么都归 document（等出现"筛选某类文书"真实需求再加） |

```jsonc
{ "id": "s-6", "type": "document",
  "name": "民事起诉状",                            // 业务叫法
  "loc": { "file": "起诉状.pdf",                   // 原始文件
           "page": 1 },                            // 可选
  "quote": "…摘录…"                                // 可选
}
```

> 边界：document = 卷内"非合同、非举证证据"的其他文书（起诉状/答辩状/律师函/传票/登记材料…）。

### 4.7 精雕定稿：web（案外在线引用）

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| `accessedAt` 访问日期 | **必填**——网页会变，不记访问时间无法复核（证据固定） |
| `platform` 平台 / `query` 检索条件 | **可选**——platform 用于展示出处站点；query 仅动态查询（B 类政务/司法记录）需要 |
| `snapshot` 内容快照 | **第一版不做**——先用通用 `quote` 摘录留存当时内容，真上庭举证时再加 |

```jsonc
{ "id": "s-3", "type": "web",
  "name": "鑫城建材-工商公示信息",                    // 业务叫法
  "title": "企业信用信息公示系统-企业信息",             // 页面原标题（可选）
  "loc": { "url": "https://www.gsxt.gov.cn/…",       // 网址，必填
           "platform": "国家企业信用信息公示系统",      // 可选：出处站点
           "query": "统一社会信用代码 91110…",        // 可选：检索条件
           "accessedAt": "2025-09-07" },             // 访问日期，必填
  "quote": "注册资本 5,000 万元，登记状态：存续"       // 摘录当时内容（可选）
}
```

> web 与卷内类本质区别：网页动态不可控，故字段围绕"时间固定 + 内容留存"设计。
> 边界：在线公示若打印提交为证据 → 归 `evidence`（type 看角色不看获取途径）。

### 4.8 精雕定稿：other（兜底）

发起人拍板（2025-09）：

| 决策点 | 结论 |
|---|---|
| 专属字段 | **无专属 loc**——other 是例外不是类型，不给例外建规则 |
| `note` 自由说明 | **要**（可选）——没有说明的 other 会让看图的人一头雾水 |

```jsonc
{ "id": "s-9", "type": "other",
  "name": "某某内部台账",              // 业务叫法
  "note": "公司内部整理的往来台账，无正式编号",  // 可选：为什么归 other
  "quote": "…摘录…"                   // 通用可选
}
```

> 升格规则：某类材料反复落进 other → 该升格为新 type（枚举加值），不是给 other 加字段。

### 4.9 收尾说明

- 7 类 source 已全部精雕定稿（§4.2–4.8）；
- 受控枚举：新增来源类别 = 枚举加值（版本化），不改结构；
- 若将来出现"来源是另一张图的表达"（如某事件引用某主张），再议，不预先设计。

## 5. sources 表放哪：已定方案 B（图内自带来源副本）
