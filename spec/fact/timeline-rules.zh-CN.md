# fact 时间图 · 排布规则 v1

> 状态：**已确认**（2026-10）。v0（2026-09）已确认的规则，除下面"v1 改了什么"列出的几条外，全部沿用。
> 范围：fact 图的**排布**规则，即“事件摆在图的哪里”。
> 关系：本文取代 `spec/fact/schema-draft.md` 第 3 节中关于分组、主体、顺序的旧规则。字段本身的定义仍以那份为准（槽结构除外，见 §4）。

> **关于方位词。** 本文一律用**方向中立**的叫法：**第 1 侧 / 第 2 侧 / 轴线**。
> 竖向下第 1 侧在**左**、第 2 侧在**右**；横向下第 1 侧在**上**、第 2 侧在**下**。
> 下面 ASCII 图按**竖向**画，图里出现的"上 / 下"就是竖向下第 1 侧 / 第 2 侧的实际位置，
> 不是规范的术语。

> **v1 改了什么。**
> 1. 分组分的是什么，看图里有几个主体：0 或 1 个主体，分组分**行为**，写在事件上；2 个及以上主体，分组分**主体**（阵营），写在主体上，事件的位置由主体推出（§2）。
> 2. **取消视角**（`views`）。一张图只有一种摆法，时间轴、时间刻度图、大事记三种画法按同一套站位来摆。
> 3. **不兼容旧数据**。生成的 HTML 自带当时的数据和程序，旧图照常打开；旧 JSON 用新版生成时报错，并说明怎么改。
>
> 为什么改：v0 里分组既管"什么性质"又管"在哪一侧"，还规定两方以上的事件只能进第 3 组。按主题分组的作者只好把"借款"（双方的行为）放进第 3 组，于是借款不在"借贷与还款"那条泳道里（方远案）。视角又给同一份数据叠了第二套摆法，写偏一点图就表达不对。

## 0. 一句话

一张 fact 时间图，就是一条轴线上的一张网格：

- **竖着的是时间**：一个槽 = 一个时间点，自上而下。
- **横着的是车道**：第 1 侧、轴线、第 2 侧，共三种站位。

```
                    上侧车道          轴 线           下侧车道
槽 1（第 1 个时间点）  [事件]         [事件]          [事件]      ← 同一行并排
槽 2                                [事件]
槽 3                                [事件]
                    ↓ 时间沿轴线向下
```

## 1. 四样东西各管什么

| 对象 | 管什么 | 有序？ |
|---|---|---|
| `slots` | **时间**。一个槽 = 一个时间点 | 有序，顺序即先后 |
| `groups` | **站位**。第 1 组第 1 侧、第 2 组第 2 侧、第 3 组轴线 | 有序，顺序即站位 |
| `actors` | **车道**。每个主体占一列，决定同一侧内的远近；2 个及以上主体时，每个主体还写明自己在第 1 组还是第 2 组 | 有序，顺序即由内到外 |
| `events` | **内容**。装在槽里；0 或 1 个主体时靠自己的 `groupId` 定侧，2 个及以上主体时由 `actorIds` 推出位置 | 无序，位置由前两者决定 |

> 一张图只有一种摆法，没有视角。

## 2. 站位：分组分的是什么，看图里有几个主体

### 2.1 0 或 1 个主体：分组分的是**行为**

只有一个当事人时，"谁在哪一侧"没有意义，两侧用来分行为的性质（按约定 / 偏离约定、行为 / 后果……，分法由 agent 按案情定）。

分组写在**事件**上（`events[].groupId`）：

| 事件的情况 | 落在哪 |
|---|---|
| 没写 `groupId` | 轴线上 |
| 写第 1 个组 | 第 1 侧 |
| 写第 2 个组 | 第 2 侧 |
| 写第 3 个组 | 轴线上（与"不写"落点相同，只是给这条车道一个名字） |

主体上不写 `groupId`，写了报错。

例：健身房案只有韩磊一人，分组是"正常（按约定履行）/ 异常（偏离约定）/ 客观经过（不涉及当事人）"。

### 2.2 2 个及以上主体：分组分的是**主体**

有两方以上当事人时，两侧就是两个阵营。分组写在**主体**上（`actors[].groupId`）：

- **每个主体必须写 `groupId`，且只能是第 1 组或第 2 组。** 第 3 组是轴线，不是阵营。
- **事件上不写 `groupId`**，写了报错。事件在哪，由它的 `actorIds` 推出来：

| 事件涉及的主体 | 落在哪 |
|---|---|
| 1 个 | 这个主体所在那一侧、他自己那一列 |
| 2 个及以上，横跨两侧 | 轴线上 |
| 2 个及以上，都在同一侧 | 轴线上（不做横跨几列的长卡片，卡片样式不变） |
| 没写 | 轴线上 |

- **两侧都不属于的第三方**（出警的民警、急救人员、送达的法院……）不列为主体：名字写进事件标题，事件不写 `actorIds`，落在轴线上。
- 刚好两个主体时，就是一组一个人。

例：方远案，方远、梁某 → 第 1 组"方远母子"，讨债方 → 第 2 组"讨债方"，第 3 组"双方交涉与客观经过"。梁某夫妇向讨债方借款 → 横跨两侧，轴线；梁某还款 → 第 1 侧梁某那一列。

### 2.3 两种情况都适用的

- **组的顺序就是站位的顺序**：第 1 组第 1 侧、第 2 组第 2 侧、第 3 组轴线。
- **组数上限 3**。轴只有两侧加中间三个位置，第 4 个组属于数据错误。
- **第 3 组可写可不写**。它的价值是给"轴线上"一个名字，好在列标题里显示；不写就靠默认规则落到同一位置。
- 分组里没有事件 = 一条空车道，不影响布局，列标题仍会出现（空位本身是信息）。
- **时间刻度图、大事记按同一套站位**：一组一条泳道（第 1 侧、第 2 侧、轴线），和时间轴一一对应。

## 3. 距离：同一侧内的主体怎么往外排

- **每一侧都从贴轴的第 1 格起算**，跨侧互不影响。
- 同一侧里有多个主体时，按它们在 `actors` 清单里的先后，一个比一个往外错一格。
- 因此，如果两个主体分居两侧（每侧各一个），**它们离轴的距离相同**，图是对称的。

```
两侧各一个主体（楼道充电劝阻案（虚构））        同一侧里有三个主体
        上侧    轴线    下侧              上侧              轴线
第 1 格  [A]           [B]            第 1 格 [A]
第 2 格                               第 2 格       [B]
第 3 格                               第 3 格              [C]
两侧离轴距离相同                      同一侧内依次往外
```

## 4. 时间槽

- **一个槽 = 一个时间点。** 同一槽里的事件**并排显示**。
- **槽的先后 = `slots` 数组的先后。** 不写编号、不写序号，顺序就是数组位置。这样拖拽换位不需要重编号。
- **`date` 只用于显示，不决定顺序。** 混合精度（有的到秒、有的只到日）时机器无法可靠比较，顺序一律听数组的。
- **同一个槽里，同一条车道最多一个事件。** 撞车即数据错误，校验层报错并指出是哪两个事件撞了。
- **轴上不画时间刻度。** 时间只在每张卡片上显示，槽本身也不写抬头。
- **空槽无意义**，不允许。

```
同一槽内允许（三条车道各一个）          同一槽内不允许（两个都落同一车道）
第 1 格 [上侧事件][轴线事件][下侧事件]        [上侧事件 A][上侧事件 B]  ← 撞车
```

事件结构（取代原来的扁平 `events` 数组）：

```jsonc
"slots": [
  {
    "events": [
      { "id": "ev-2", "date": "2030-06-02T20:14:07", "label": "孙浩进入楼道",
        "actorIds": ["a-1"] },
      { "id": "ev-1", "date": "2030-06-02T20:14:03", "label": "钱敏在楼道内充电",
        "actorIds": ["a-2"] }
    ]
  }
]
```

## 5. 两条配套约定

- **`actorIds` 的含义是“这个事件涉及谁”，不是“这是谁做的”。** 可选。收到短信这种事件涉及收信人，应当写上；闸机停用、120 到达这类不涉及任何当事人的，不写，落在轴线上（0 或 1 个主体的图也可以归入第 3 组）。
- **判断顺序不依赖 `date`。** 排序、分槽的依据全部来自 `slots` 数组位置，`date` 仅在卡片上显示。

## 6. 完整示例：楼道充电劝阻案（虚构）（节选）

```
                    上侧(孙浩)         轴 线              下侧(钱敏)
20时14分           [孙浩进入楼道]   [双方言语交流]      [钱敏充电]
                                   ↑ 三条车道同一槽并排
9时28分                            [走至单元门口]
9时31分                            [呼叫 120]
（日级精度）                                           [钱敏突发不适]
```

> 左侧的时刻来自卡片自身，轴上不另画时间刻度。

```jsonc
"actors": [
  { "id": "a-1", "name": "孙浩", "role": "被告 · 劝阻方",   "groupId": "g-1" },
  { "id": "a-2", "name": "钱敏", "role": "原告 · 被劝阻方", "groupId": "g-2" }
],
"groups": [
  { "id": "g-1", "label": "孙浩一方" },        // 第 1 组 → 上侧
  { "id": "g-2", "label": "钱敏一方" },      // 第 2 组 → 下侧
  { "id": "g-3", "label": "双方共同或客观经过" }  // 第 3 组 → 轴线
],
"slots": [
  { "events": [ /* 20时14分：三件事同时，分居三条车道 */ ] },
  { "events": [ /* 9时28分 */ ] },
  { "events": [ /* 9时31分 */ ] },
  { "events": [ /* 钱敏突发不适，date 仅到日 */ ] }
]
```

## 7. 本轮不做

| 项 | 说明 |
|---|---|
| `dateEnd` 的图形化 | 文字版已做（卡片写「起 - 止」、浮层给时长）。跨槽的竖条**不做**：槽是等距的而真实时间不是（楼道案里 4 秒和 264 秒占的图上距离一样），按真实时长画长度会骗人 |
| 横竖切换 | **已做**。方向是渲染参数，逻辑不随方向变；默认值按槽数取（槽 ≥ 5 竖向、≤ 4 横向） |
| 三个以上主体的专门验证 | **已验**：4 个主体、5 列的示例 |
| 拖拽编辑 | 结构已为它留好路（顺序靠数组、同槽靠嵌套），功能不做 |
| 轴上的时间刻度 | 不画。时间只在卡片上显示，避免混合精度下刻度误导 |

## 8. 已收口

| 争议点 | 结论 |
|---|---|
| 事件涉及 ≥2 个主体、又写了侧别组 | v0：**报错**。v1：2 个及以上主体时事件不写组，这种矛盾不会再出现 |
| 视角（`views`） | **v1 取消**。一张图一种摆法；视角写偏一点图就表达不对，对能力弱的 agent 尤其难 |
| 同一侧几个人一起做的事 | **落轴线**。不做横跨几列的长卡片，卡片样式不变 |
| 多主体的图按行为分两侧 | **不支持**。多主体时两侧就是阵营；行为性质写在事件标题或摘要里 |
| 旧数据 | **不兼容**。HTML 自带当时的数据和程序，旧图不受影响；旧 JSON 用新版生成时逐条报错，说明怎么改（删 `views`、把分组从事件挪到主体上） |
| 混合精度下槽刻度会误导 | **轴上不画时间刻度**，时间只在卡片上显示，从根上避免误导 |
| `groups[].label` 与 `events[].label` 同名 | **保持现状**。`name` 是“它叫什么”，`label` 是“这儿显示什么字”：主体、来源用 `name`，分组、事件用 `label`。为求表面整齐把分组改成 `name` 反而牺牲语义 |
