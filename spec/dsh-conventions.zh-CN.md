# 在 DSH 自己的约定内构建 DSH 插件

> 状态：**对 `tools/dsh/` 下的一切生效**。按 DeepSeek Harness **0.2.0-rc.2** 编写。产品决策（维护者，2026-10）：插件要建在 **DSH 官方约定之内**，而不是绕开它们。只要 DSH 为某件事提供了扩展点，我们就用它；不把状态复制进私有存储，不自己监听 DOM，也不伸手进内部实现。插件自身的设计在 [dsh-plugin.md](dsh-plugin.md)；本文是它必须遵守的规则书。

## 1. 什么算“官方”

按权威性排序：

1. **随已安装 DSH 一起发布的包 README**：`node_modules/@deepseek-ai/<package>/README.md`。它们描述公开面（`ctx.<service>`）、席位（slots），以及有意不提供的东西。本插件涉及的包有：`dsh-client-ui-sidebar-right`、`dsh-client-resources`、`dsh-client-shortcuts`、`dsh-client-ui-shortcuts`、`dsh-client-ui-tool`、`dsh-client-locale`、`dsh-tools`。
2. **已经做同样事情的官方插件**，当作完整示例来读：`dsh-client-ui-plan`（资源类型、provider、标签页正文、回合末尾）、`dsh-client-ui-deliverables`（回合末尾、工具行）、`dsh-client-ui-sidebar-documentpreview`（资源类型）。
3. 别的都不算。只有在浏览器里试出来的行为，或只在 bundle 内部看到的行为，**不是**契约：不要建立在它上面。

**第一次使用某个 DSH API 之前**，要在 (1) 或 (2) 里找到它，并在 PR 里写明文件和章节。**两边都没有写，就不要用**：去问维护者。无法避免的偏离要写进 §4，连同原因和将来移除它的 issue。

## 3. 怎么工作

1. **按 README 做计划。** 给 DSH worker 的 brief 要写明 README 章节和可供照抄模式的官方插件（路径是 `node_modules/@deepseek-ai/…`）。
2. **对照 §2 审查。** 每个动到 `tools/dsh/` 的 PR 都要说明它依赖哪些规则。审查者会拒绝裸 DOM 监听、私有存储，以及 §1 之外的任何 DSH 内部实现。
3. **在真实 DSH 里测**（headless 和 web profile；见 `CLAUDE.md`）：先测功能，再测**页面刷新**，再测关闭后重开，因为大多数偏离都藏在刷新后仍然存活的东西里。
4. **新的 DSH 版本会重新打开本文。** 移动支持范围之前，再读一遍 §1 里各包的 README。

记下的唯一偏离：共享组件和官方 bundle 一样通过 ModuleLoader `require` 取得，手写回退行存在是因为这条解析路径没有对第三方插件作出文档说明。已在真实 DSH（0.2.0-rc.2）中确认：`require` 可以解析；`DisclosureRow` 和图标是 `React.memo` / `forwardRef` 对象而不是函数，所以判断接受任何 React 组件类型。插件必须像官方插件一样把 `locale` 写进自己的 `inject`：否则 `apply` 时 `ctx.locale` 为 undefined，会悄悄退回英文。

DSH 公开面没有覆盖、因此保持原样并列在这里：**刷新后的“Open HTML”。** 聊天卡片的 `openFile` 只在该卡片挂载期间存在，所以恢复后的大图无法打开写出的文件。修法会通过 DSH 自己的 file resource address 打开文件；需要单独设计。
