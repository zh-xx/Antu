## 0. 本轮定下的六个决定

1. **数据模型用自由图 `nodes` + `edges`**，不用“主线数组 + 分支挂载”的分层结构。
   理由：scheme 只到大类，装得下就不改结构。分层结构省布局，但将来做泳道图、状态图时装不下，
   一改 schema 就废掉已有的 JSON（见 §7 第 1 项）。
2. **主干标在边上**（`main: true`），不标在节点上。理由：主干是一条**路径**；标在节点上会出现
   “标了主干但链断了”这种校验不出来的错误。不标时由渲染层推断（见 §4.1）。
3. **`kind` 收敛到 6 种形状**；旧原型的“正/负结果”不是形状，独立成 `outcome` 字段（见 §4.3）。
4. **有 `stages`（阶段）**，节点用 `stageId` 引用。合同流程天然分阶段；没有它，agent 只能像
   现在的 Mermaid 输出那样把“第一阶段”写进节点文字，把阶段和步骤混在一起（见 §4.4）。
5. **procedure 没有 `views`**。视角是 fact 的概念（同一批事实换立场看），程序流程没有这一维。
6. **`sources` 复用 fact 的 7 类与结构化定位**，不另立一套（见 §4.7）。

要点：

- **节点是节点，边是边。** 节点只说“流程里有什么”，走法全在 `edges` 里。
  这样同一份数据才能既画流程图，又画将来别的画法（泳道图、状态图）。
- **条件不是节点。** “通过 / 未通过”这些判断结果写在**边的 `condition`** 上，
  不写成节点。写成节点会让节点数量翻倍，而且判断归属不清。
- **回边就是普通边。** “整改到合格为止”在数据里就是一条指回上游的边，
  不写 `type: "loop"` 之类的标记，由渲染层从图结构里认出来（见 §4.6）。
- **主干是标注，不是新结构。** 标 11 条 `main: true` 就说明白哪条是主线，
  不需要把节点拆成两套。
- 真实合同里“延期判断”在三个阶段各出现一次。上面只写了需求确认阶段那一份，
  其余两次结构相同（`n-3`/`n-6`/`n-10` 各挂一组），示例从简。

> **这份示例已按 §5 的 18 条规则机器跑过一遍**：17 个节点、21 条边、5 个阶段、
> 入口唯一（`n-1`）、主干链 12 个节点（`n-1` → … → `n-15`），全部通过。
>
> 它是**节选**：真实的 01 那份 `.mmd` 是 26 个节点、34 条边、9 条回边、最长链 12 层
> （见 §8 实测表）。示例只保留了一个阶段的延期分支，其余两处结构相同。

## 3. 字段规则

### 图级字段

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `domain` | ❌ | string 枚举 | 整张图属于哪一类流程，见 §4.2 |
| `actors` | ❌ | object[] | 主体清单：`{ id, name, role? }`。与 fact 同形同义 |
| `stages` | ❌ | object[] | 阶段清单（有序）：`{ id, label }`。见 §4.4 |
| `sources` | ❌ | object[] | 图内来源表，7 类与定位字段完全复用 fact，见 §4.7 |
| `nodes` | ✅ | object[] | 流程里的节点，见下 |
| `edges` | ✅ | object[] | 节点之间的走法，见下 |

### `nodes[]` 每项

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | ✅ | string | 全图唯一，供 `edges` 引用 |
| `kind` | ✅ | string 枚举 | 形状：`start` / `step` / `decision` / `end` / `document` / `note`，见 §4.3 |
| `label` | ✅ | string | 节点上的一句话，一行约 12 字、最多两行 |
| `detail` | ❌ | string | 金额、期限、条件等补充。盒内显示首行，浮层显示全文 |
| `actorIds` | ❌ | string[] | 引用 `actors` 的 id。**只用于显示（标在节点上），不用于分列**，见 §4.5 |
| `stageId` | ❌ | string | 引用 `stages` 的 id |
| `outcome` | ❌ | string 枚举 | `positive` / `negative` / `neutral`，默认 `neutral`，见 §4.3 |
| `sourceIds` | ❌ | string[] | 引用本图 `sources` 的 id |

### `edges[]` 每项

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `from` | ✅ | string | 起点节点 id |
| `to` | ✅ | string | 终点节点 id |
| `condition` | ❌ | string | 通行条件（人读短语），如“通过”“乙方原因”。**`kind=decision` 的出边必填**，见 §4.5 |
| `main` | ❌ | boolean | 标这条边属于主干。不标时由渲染层推断，见 §4.1 |

**没有 `summary` 字段**（与 fact 不同）。fact 需要 `label`/`summary`/`detail` 三个字段，
是因为卡片每加一行，整张图高 +126px，全览缩放掉一档、整张图字号小 15% 到 19%
（见 `spec/fact/schema-draft.md`）。流程图的节点是方块，不是等高卡片，没有这个连锁反应，
所以 `label` 与 `detail` 两个足够。这条可以改，但它牵动节点尺寸的计算。

## 4. 各机制

### 4.1 主干机制

**主干 = 从入口到终点的那一条主线，图上居中显示。**

标在边上而不是节点上：

| 标在哪 | 后果 |
|---|---|
| **边**（本草案） | 主干是一条路径，标注与语义一致；“从入口沿 main 边能不能走到 end”可以校验 |
| 节点 | 会出现“标了 main 但两条出边都没标”这种断链，而校验查不出来（它只看到一堆孤立的标记） |

数据没标 `main` 时，渲染层按下面的顺序推断，保证任何合法 JSON 都排得出来：

```
从入口节点出发，每一步取“主出边”，依次判断：
  ① 这条边显式标了 main: true          → 选它
  ② 出边里第一条 condition 为空、且目标节点未被访问 → 选它
  ③ 都不满足 → 取 edges 数组里的第一条未访问出边
走到 kind = "end" 的节点即停。
```

标了 `main` 而断链时，校验层报错（见 §5 第 16 条）。**不自动补边**。

**第 ③ 条不是装饰，是必需的。** 实测（§8）：走到菱形节点时，它的出边**全都带 `condition`**，
只靠 ①② 会在第 4 步就停住，主干断在半路。

但 ③ 的选择是任意的（取 `edges` 数组第一条），所以在菱形上不标 `main` 时，
主干可能不是写数据的人想要的那条。因此加一条提示（不报错）：

```
菱形位于主干上（有一条 main 入边）、有 2 条以上出边、却没有一条标 main
  → 提示：建议标出哪条是主干
```

**这条提示只对“主干上的菱形”生效。** 挂在主干之外的侧向检查不算：
例如示例里的 `n-5`（“本阶段是否发生延期”），它整个是一条支线，两条出边都是回边，
本来就不该有主干出边。规则不区分这两者的话，真实数据里每一个侧向判定都会被误报。

菱形选错主干的表现是：违约路径被画成主线，正常履行被挤到旁边。校验拦不住这件事
（两条路都合法），只能靠提示让 agent 自己看一眼。

### 4.2 `domain`：这张图属于哪一类流程

```
"domain": "contract-performance"

litigation              诉讼程序（立案 / 审级 / 执行）
administrative          行政程序（申请 / 复议 / 决定）
contract-performance    合同履行流程
approval                内部审批路径
negotiation             谈判 / 磋商推进
other                   其它
```

为什么合同流程与诉讼程序**共用一个 schema、靠枚举区分**，而不是新开第五个大类：
`spec/v0-architecture.md` §3 定了判据，**成为新顶层类型的唯一条件是“元素结构装不进现有类型”**。
合同流程与诉讼程序都是“步骤 + 条件分支”，元素结构完全一样，装得下，所以只能是受控枚举。

**这一项可选**，且当前渲染不读它。留它的理由是：跨图归档时能一眼看出流程的类别，
将来按领域取默认参数也有依据。若发起人认为它属于“分类枚举无实质收益”（fact 当初否掉
`kind` 就是这个理由），删掉它不牵动任何别的东西。列在 §7 待表决。

### 4.3 节点形状（`kind`）与结果（`outcome`）

**`kind` 定形状，`outcome` 定画法（各主题里正面结果都是更粗的线、负面结果都是虚线，颜色由主题加上），两个维度不混。**

| `kind` | 形状 | 用在 |
|---|---|---|
| `start` | 圆角矩形 | 流程的入口，通常只有一个 |
| `step` | 矩形 | 一个动作、一件事、一个阶段产物 |
| `decision` | 菱形 | 判断点，出边 ≥ 2 条且每条带 `condition` |
| `end` | 双线圆角矩形 | 流程终点，至少一个 |
| `document` | 文档形（下边波浪） | 产出的文件、凭证、单据 |
| `note` | 无边框 + 折角 | 说明性文字，不参与流程（可以没有出边） |

六种是**形状**的封闭集合。旧原型有 9 种，多出来的是 `outcome-positive` / `outcome-negative`，
它们与 `step` 形状相同、只是颜色不同，**那是结果属性不是形状**，所以拿出来做独立字段：

```
"outcome": "negative"      // positive / negative / neutral（默认 neutral）
```

映射关系（旧原型四种配色 → 新三值）：

| 旧 prompt 里的配色 | 新写法 |
|---|---|
| 正常履行节点 `#e6e6fa` | 不写（默认 `neutral`） |
| 违约节点 `#ffff99` | `"outcome": "negative"` |
| 完成节点 `#90ee90` | `"outcome": "positive"` |
| 终止节点 `#ff6666` | **看语义**：正常终止写 `neutral`，失败终止写 `negative` |

最后一行是这套设计要解决的问题：旧做法把“终止”一律涂红，但示例里“项目完成 → 合同终止”
是正常收尾，涂红是错的。**同一个标签在不同合同里可以是正常或异常，只有读合同的人知道，
所以它必须是数据字段，不能写死在提示词里。**

### 4.4 阶段（`stages`）

`stages` 是图级有序清单，节点用 `stageId` 引用。渲染时画成阶段框（把该阶段节点框起来的浅底色分组框，左上角写阶段名）。

**为什么值得单独一个字段。** 现在的 Mermaid 输出把阶段写进了节点文字：

```
C[第一阶段：需求确认 2026-06-30前]      ← 阶段与步骤混在一个节点里
```

后果是：阶段的边界画不出来，同一阶段的节点在图上散开，读者要靠文字自己拼。
有了 `stages`，阶段成为**结构**，图上可以画出来，也可以据此给节点分组。

- 不写 `stages` 就不画阶段框，其余画法不变；
- 写了 `stages` 但某个节点没写 `stageId`，它不属于任何阶段，照常渲染；
- `stageId` 引用不存在的 id → 报错。

### 4.5 条件（`condition`）与主体（`actorIds`）

**`condition` 是第一等公民。** 合同流程图的全部法律含义几乎都在这些短语里
（“通过 / 未通过”“甲方原因 / 乙方原因”“合格 / 不合格”）。

- 字段名叫 `condition` 而不是 `label`：`label` 在 fact 里的含义是“这儿显示什么字”，
  而这里是“这条边什么条件下走通”，是语义不是文案。全项目一套词汇，避免一个词三种用法；
- `kind = "decision"` 的每条出边**必须**有 `condition`，缺了报错；
- 非 decision 节点的出边可以有也可以没有；有就显示，没有就画一条干净的线。

**`actorIds` 只用于显示。** 节点上标出“谁做的”（如节点角上一行小字），
但**不据此分列**。按主体分列是泳道图的事，那是 procedure 的第二个子类，不是本子类的参数。
第一版把它限定成显示用途，是为了不走旧项目那条路（旧原型的 `swimlane` 至今停在 `enabled: false`）。

**一个节点可以有多条出边，不限于 `decision`。这条是实测逼出来的，不是可选项。**
7 份真实合同里有 4 份用到，共 15 个节点：01 的 3 个、03 的 2 个、06 的 6 个、07 的 4 个。
最极端的一份（06）整张图**一个菱形都没有**，分支全靠“普通节点挂多条出边”表达。
示例里 `n-3`（需求确认）也是如此：一条主干通向判定点，一条带 `condition: "延期"` 通向延期判断。

校验层不禁止，渲染规则是：**标了 `main` 的那条走在主干上，其余出边按分支列展开。**
只有 `decision` 才有“出边必须 ≥ 2、且每条必须带条件”的硬要求。

### 4.6 回边

“整改到合格为止”在这类合同里是常态，所以回边必须支持，而且必须画得能看。

- **数据里回边就是普通边**，不写标记；
- 渲染层识别：从入口做一次遍历，指向“已经访问过且不在当前路径之外”的边即为回边；
- 画法：回边绕主干一侧画弧线，不参与分层（不把层号往回拉）；
- **限制**：回边只允许回到更上游的节点，跨度不做限制，但同一对节点之间不允许出现两条回边。

用标记（如 `"loop": true`）的坏处：agent 要自己判断哪条是回边，判错就画不出来；
而渲染层本来就要遍历一遍图，顺手就能认出来。

### 4.7 来源（`sources`）与“没有视角”

- **`sources` 完全复用 fact 的定义**：7 类（`statute` / `case` / `contract` / `evidence` /
  `document` / `web` / `other`），结构化定位字段按 type 精雕（合同的 `loc` 是
  `{ file, clause(数字), page }`）。见 `spec/source-schema-draft.md`；
- 节点用 `sourceIds` 引用；悬空引用报错；
- **procedure 没有 `views`**。视角是 fact 的机制（同一批事实换立场看）；
  程序流程没有“立场”这一维，不需要多套看法。写进这里是为了防止以后有人照 fact 的样子加。

## 5. 校验规则清单（跨字段，逐条报错）

字段表（`PROCEDURE_FIELDS`）只管字段级规则；下面是跨字段规则，由校验器逐条报出，
**报错格式带字段路径与节点/边 id**，照 fact 的样式：

```
nodes[4] (n-5): kind "desicion" 不在词表内（start/step/decision/end/document/note）
edges[7]: `to` 指向不存在的节点 "n-99"
nodes[2] (n-3): 非 end 节点必须有出边，否则流程断在这里
```

| # | 规则 | 报错还是提示 |
|---|---|---|
| 1 | `domain` 若写了，必须在枚举内 | 报错 |
| 2 | `nodes` 非空、`edges` 非空 | 报错 |
| 3 | `node.id` 全图唯一 | 报错 |
| 4 | `node.kind` 在六种之内 | 报错 |
| 5 | `node.label` 必填且非空 | 报错 |
| 6 | `actorIds` / `sourceIds` / `stageId` 引用的 id 必须存在 | 报错 |
| 7 | `edge.from` / `edge.to` 指向存在的节点 | 报错 |
| 8 | 禁止自环（`from === to`） | 报错 |
| 9 | 禁止重复边（同一 `from` + `to` + `condition` 出现两次） | 报错 |
| 10 | 至少一个入度为 0 的入口节点；入口是 `start` 节点（没有 `start` 时取第一个无入边的节点）。其余无入边的节点（`note` 和规则的 `endId` 除外）是孤儿（issue #18） | 报错 |
| 11 | **所有节点必须从入口（`start` 节点）可达**（没有任何边通向的环，否则会被静默丢失，界面上看不出来） | 报错 |
| 12 | 至少一个 `kind = "end"` | 报错 |
| 13 | 非 `end`、非 `note` 的节点必须有出边（流程断在这里） | 报错 |
| 14 | `kind = "decision"` 的出边必须 ≥ 2 条 | 报错 |
| 15 | `kind = "decision"` 的每条出边必须有 `condition` | 报错 |
| 16 | 标了 `main: true` 时，从入口沿 `main` 边必须能走到某个 `end`（断链） | 报错 |
| 17 | `outcome` 若写了，必须在枚举内 | 报错 |
| 18 | 数组顺序与 `stages` 顺序明显矛盾（某节点的 `stageId` 排在它上游节点之前） | 提示，不报错 |
| 19 | 主干上的菱形有 2 条以上出边，但没有一条标 `main` | 提示，不报错（见 §4.1） |

第 11 条与 fact 的“一格一事件”是同一类规则：**都是防止内容被静默丢掉。**
`fact/timeline/layout.js` 的注释把理由写得很清楚，这里照抄那条立场。

第 14、15 条是“判定点必须真的是判定点”：只有一个出边的菱形没有意义，
没有条件标签的分支读者看不懂往哪走。

**第 15 条的报错要给出改法**，因为实测里真出现了这种数据（§8）：03 的
“每月 25 日前乙方提交服务清单及发票”被画成菱形，它的主出边没有条件。那个节点其实是
**过程节点不是判断点**，所以报错信息不该只说“缺 condition”，要说清两条路：

```
nodes[2] (n-3): kind 是 decision，但出边 edges[1] 没有 condition。
  · 若这确实是一个判断点 → 给每条出边补上 condition（如“通过 / 未通过”）；
  · 若它其实是一个过程 → 把 kind 改成 "step"（过程节点允许多条出边，其中一条走主干）。
```

**不做自动修复。** 旧原型有一层 `postProcessLegalFlow`，会自动去重边、把孤立节点接回去、
给判定点补标签。案图的立场是“校验报错，让 agent 自己改”：自动修复会把 agent 的错误吞掉，
下一次它还犯。要区分的是：

| 类别 | 处理 |
|---|---|
| 数据错误（悬空引用、孤立节点、判定点出边不足） | 校验报错，不修 |
| 排版容错（同层节点顺序、回边绕哪一侧） | 渲染层给默认值，不报错 |

## 6. 呈现（渲染层的工作）

数据层不关心这些。同一份 JSON 换画法，数据一个字不改（`spec/v0-architecture.md` §3 的硬约束）。

### 6.1 第一个子类 `flow`（流程图）

**实现进度（2026-09）**：流程图已经能画出来，代码在
`src/renderers/procedure/flow/`（rules.js 校验、metrics.js 尺寸、layout.js 排布、palette.js 配色、
FlowRenderer.jsx 及节点 / 连线 / 阶段框组件），单元测试在 `test/procedure-layout.test.mjs`，
浏览器检查在 `npm run verify`。已做与未做：

```
已做  阶段分栏（flow/columns.js）：每个阶段单独交给 ELK 的分层算法排（elkjs，flow/elk.js），主干边优先保持笔直；
      远比其他阶段高的阶段在框内折成两栏；阶段可左右镜像，让朝向下一阶段的一侧空出来；
      阶段之间的线由自写的正交寻路走（flow/router.js：折数最少、其次最短，避开节点、阶段名和标签，
      进每个节点前有 11px 的直线）；为每个条件标签预留位置；回边识别（画虚线）、同目标多边合并、两个方向；
      条款作为图下方的表（flow/ruleTable.js）；React 渲染器（按 kind 六种形状、
      按 outcome 三种画法、悬停 / 钉住浮层带出处）、按文字定大小的节点、阶段框、控制胶囊（§6.2）、导出图片
未做  **note 节点的定位**（它不参与流程，ELK 把它当普通节点摆）
```

实测（7 份合同加两份规则层草案，两个方向）：

| | 手写排布（已替换） | dagre | **ELK（在用）** |
|---|---|---|---|
| 交叉，01 | 12 | 7 | **0** |
| 交叉，03 | 38 | 11 | **2** |
| 交叉，其余五份 | 12 | 1 | **0** |
| 标签压在节点上 | 靠规则避开 | 0 | **0**（ELK 预留位置） |

单元测试卡住的：连线不从节点背后穿过、两条不同的线不叠在一起、标签不压任何节点、
连线落在节点轮廓上（菱形落在斜边上）、主干很少拐弯（140 段里 10 段）、没有线折三次以上，阶段框只装自己的节点、互不重叠。

为什么换成 ELK：手写排布把主干固定成一列，其余全挂在它两侧。主干因此很死板，
其他分支只能横穿它，交叉数就是代价。ELK 把主干当成偏好（边的优先级）而不是一列，
对整张图做交叉最小化。**代价**：elkjs 约 1.4 MB，生成的 HTML 从约 480 KB 变为约 1.9 MB。
它是同步调用的（怎么做、为什么，见 `flow/elk.js` 文件头），elkjs 的版本已锁定。

渲染层定下的几件事，写在这里免得被无意改回去：

- **阶段分栏**（`flow/columns.js`）：画阶段且每个节点都有阶段时，每个阶段一个框，框从左到右排，
  框内从上往下走（横排时整体转置）。整张图作为一个图排，不论哪个方向都是长条（01：750×1610 或
  2388×412），分栏后 01 是 1390×578。每个阶段单独交给 ELK 排（ELK 一次排不出"框横排、框内竖排"：
  实测要么把阶段叠起来且有线没走，要么忽略框内方向）；跨阶段的线由 `flow/router.js` 寻路（折数最少，
  其次最短；避开节点、阶段名和标签；不贴着框边走）。远比其他阶段高的阶段在框内折成两栏；阶段可以左右
  镜像，让朝向下一阶段的一侧空出来；回线和主干交叉时回线让路，除非要多折一次以上。没有阶段、或只有
  部分节点有阶段时，仍按整张图排，阶段画成 ELK 的复合节点。
- **框按文字定大小**（`metrics.js` 的 `sizeOf`）：字号 14，超过上限换行，最多三行；菱形把文字折成
  近似方块。固定 208×64 的框大半是空的，适配屏幕后字小到读不清——这是把同一份数据交给 Mermaid 画后看到的。
- **线尽量少折：优先直线，其次折一次**（`flow/straighten.js`）。ELK 的布线规定线从节点底部出、
  顶部进，所以两个没对齐的节点之间就是 Z 形（折两次），回边折四次。ELK 排完后，每条线按折数从少到多
  试更简单的走法：直线；从侧边出、向下进顶部（判断节点最常见的出法）；从底部出、横着进侧边；回边直接
  回去或绕成 U 形。只有不压任何节点、阶段名、标签，不与别的线重叠，也不增加交叉时才换。另外会用几种
  节点摆放方式各排一次，留折得最少的那张。实测（全部合同、两个方向）：折点从 132 个降到 62 个，
  没有一条线折三次以上。
- **直线 / 曲线**是展示选择（§6.2）：曲线版走同一条路线，只是每个拐角画成大圆弧，
  所以切换时节点和标签都不动。
- **主干高亮跟着引擎定下的主干走**，不论是标了 `main: true` 还是推断出来的，
  所以一张没标 `main` 的图也看得到主干。

实测（7 份真实合同，两个方向都排得出）：01 十二层、05 十六层、06 二十层；
03 有 3 条边被并成 2 条连线；01 认出 12 条回边、07 是 0 条。

- **主干居中**，分支节点分列左右；同层多个分支按 `edges` 数组里的出现顺序左右展开；
- **阶段框**：写了 `stages` 就把每个阶段的节点框起来并写阶段名；
- **边**：主干边直连；分支边带 `condition` 标签并预留标签宽度；回边绕主干一侧画弧；
- **节点**：`label` 显示，`detail` 显示首行（超出截断），浮层显示全文与来源；
- **形状与画法**：按 §4.3 的映射；
- **方向**：竖向（自上而下，默认）/ 横向（自左向右）。与 fact 一样是渲染参数，不进数据。

三条由实测逼出来的规则（§8 有证据）：

**一、主干以外的出边，按分支列展开，不管源节点是不是 `decision`。**
7 份里 4 份用的都是普通节点挂分支。渲染时只看“这条边标没标 `main`”，不看源节点形状。

**二、指向同一目标的多条边合并成一条，条件合并显示。**
03 的 `B` 有 7 条出边，其中 3 条指向同一个 `N`、2 条指向同一个 `O`，条件各不相同。
若画成 5 条并排的线会糊成一片。合并后标签写成：

```
N  ← 乙方连续 3 个月无法满足 80% 用人需求 / 未依法签劳动合同被查处 / 因乙方原因被劳动监察处罚
```

**三、终点可以有多个，并排显示。**
07 有 9 个终止节点（退还双倍定金 / 没收定金 / 仲裁裁决 / 违约赔偿…），05 有 4 个，
01 有 4 个。同层的多个终点按 `edges` 顺序并排，用 `outcome` 的画法区分是好结果还是坏结果。
**不合并、不省略**，它们是真的不同结局。

### 6.1a 第二个子类：`route`（路线图；issue #95）

> 本节状态：**已实现，初步尝试**（未确认）。没有增加任何 JSON 字段。

主线画成一条线，从左往右，像路线图；流程回头或提前结束的地方挂在线的下面。代码在 `src/renderers/procedure/route/`。流程图读作“阶段分栏、节点自上而下”；这张读作“一条线走到底，哪里会出问题”。

- **线**就是主线，找法和流程图一样（标了 `main` 的边，否则取第一条无条件的边）。线上每个节点是一个**站**，间距均匀（挂了分支的地方更宽）：步骤是圆，判断点是菱形，开始是圆点，结束是方块，`document` 是小纸页；圈或方块按 `outcome` 着色。标签写在线的上面，参与方名字（`actorIds`）在标签上方；`detail` 是鼠标悬停的提示。站与站之间至少 128 px，标签最多折成四行。
- **阶段**是一个阶段的几个站后面的色带（连续同阶段的站成一条带；没有阶段的站没有带）。
- **下挂**：从一个站出来的每条其他边，在它下面开一条分支，框一个接一个往下，条件写在最上面。分支从每个框沿第一条出路画下去，直到：(a) 到一个结束（结束框，着色）；(b) 回到线上的某一站（虚线连回去；不是它自己也不是相邻的那站时，画成图下方的弧）；(c) 走到已经画过的节点（并入）；(d) 画满第四个框，这时写“……还有 N 步”。框里其他的出路不再画，只计个数。
- **弧**在下挂分支的下面：两个站之间不沿着线走的边：回到前面的（虚线）或跳到后面的（灰色）。条件写在弧上。
- **没画出来的，会说明**：没有任何分支走到的节点（只有规则会走到的结束就是一个）、没有画出的分支，以及规则条数（规则表在流程图里）。所以每个节点要么在图上，要么列在图下面。
- 主线很长时图很宽；它以看得清的缩放（不小于 0.8）从左边打开，读者左右拖动。

### 6.3 规模怎么算、摆不下怎么办

流程图的“摆不下”与时间图不同。时间图有一条客观硬规则（一格一事件），
流程图没有对应的硬规则，所以分成两种处理：

| 类别 | 判据 | 处理 |
|---|---|---|
| **结构错误** | §5 的第 10 到 16 条 | 校验报错，不画 |
| **规模提示** | 层数、最宽层、节点总数、内容尺寸、适配缩放 | 只报告数字与建议，不报错 |

规模数字由 MCP 的 `antu_layout` 报出来（层数、最宽层、内容多大、屏幕适配缩放多少），
由 agent 判断要不要拆图。**不写死阈值**，因为真实合同里 06_工程总承包那份的规模
可能到三四十个节点，写死了会把合法数据拦下；而不写死又能让 agent 看到风险。

| 1 | 数据模型用自由图 `nodes` + `edges`，还是“主线 + 分支”分层结构？ | **自由图**。理由：schema 只到大类，将来泳道图、状态图要吃同一份 schema | 改成分层结构是重写 schema，所有示例作废。这是五项里最贵的一项 |
| 2 | `main` 标在边上还是节点上？ | **边上**。理由：主干是路径，节点上标注会出现校验不出的断链 | 改到节点上，同时校验第 16 条要重写 |
| 3 | `kind` 定 6 种、`outcome` 独立，还是沿用旧原型的 9 种？ | **6 种 + 独立 `outcome`**。理由：正负结果是属性不是形状 | 改回 9 种，则“终止”一律涂红的问题保留 |
| 4 | 要不要 `stages`？ | **要**。理由：contract 流程天然分阶段，没有它阶段只能混在节点文字里 | 删掉 `stages` 与 `stageId`，删掉渲染的阶段框，其余不动 |
| 5 | `domain` 要不要（fact 当初否掉了分类枚举）？ | **要，但可选、渲染不读**。理由：它分类的是整张图不是元素，且将来按领域取默认参数有依据 | 删掉，不牵动任何别的东西 |

### 8.1 翻译时的三处判断（都不是新增字段）

1. **01 补了三条回边。** 原始 `.mmd` 里“工期顺延”是断头路（`O`/`S`/`W` 三个节点没有出边），
   而它不是终点。按语义补成 `工期顺延 → 回到本阶段`，否则规则 13 会拦下。边数因此 34 → 37。
2. **03 把“每月提交服务清单”从菱形改成 `step`。** 原始 `.mmd` 画成菱形，但它的主出边
   没有条件，实际是过程节点（规则 15 会报错，报错话术见 §5）。
3. **01 的三条分支补了 `condition: "延期"`。** 原始 `.mmd` 里 `C → N` 这类边没有标签，
   而 `N` 是“是否甲方原因导致延期”，语义明确。除此之外**没有增删任何条件**：
   06 那份一个条件都没有，也照原样保留（它就是用来测“分支无条件时渲染层怎么办”的）。

### 8.2 结论：装得下，不用改结构

**7 份全部能落进 `nodes` + `edges` + `kind` + `stages` + `condition` + `outcome` + `main`，
一个字段都不用加。** 七份全是单一入口、零不可达节点，规则 10 与 11 没有误报。

## 10. 与 fact 的对照

| 维度 | fact | procedure |
|---|---|---|
| 核心结构 | `slots[].events[]`（线性叙事） | `nodes` + `edges`（图） |
| 位置由什么决定 | `groupId` 定侧、`actorIds` 定列 | 图结构（主干 + 分支 + 回边） |
| 时间/顺序 | `slots` 数组顺序即先后 | 图的拓扑结构，没有全局顺序 |
| 分类枚举 | **没有** `kind`（事件类别不做枚举） | **有** `kind`（六种形状，渲染必需） |
| 结果属性 | 无 | `outcome`（正/负/中性） |
| 分组 | `groups`（分侧） | `stages`（阶段）+ `kind`（形状） |
| 多套看法 | `views`（视角） | 无 |
| 文字分工 | `label` / `summary` / `detail` | `label` / `detail`（无 `summary`，见 §3） |
| 引用 | `actorIds` / `groupId` / `sourceIds` | `actorIds` / `stageId` / `sourceIds` |
| 来源 | 同一套 7 类与结构化定位 | **完全复用** |
| 摆不下的判据 | 一格一事件（结构规则，报错） | 结构错误报错；规模只提示（见 §6.3） |

一句话概括差别：**fact 是“一条时间线上的叙事”，procedure 是“一张图上的走法”。**
前者靠数组位置定顺序，后者靠边定走法；前者的分类是多余的，后者的形状是必需的。

## 11. 规则层（v1.1）

> 状态：**已并入 v1.1**（发起人，2026-09）。`rules` 是可选字段，v1 的 JSON 全部仍然有效。
> `examples/procedure/` 的七份合同都已按它改写（02 不需要规则）。

### 11.1 为什么要有

流程图渲染出来之后，把 7 份语料按结构量了一遍，发现复杂度大半不是流程本身带来的：

| 现象 | 证据 | 根源 |
|---|---|---|
| **回边几乎全是假的** | 27 条回边，27 条指回主干，如“乙方支付违约金 → 回到需求确认” | 规则 13（非终点必须有出边）逼 agent 给后果节点补一条“回去”的边；§8.1 第 1 条就是这么补的 |
| **同一条款被复制** | 01 的 26 个节点里 12 个是重复的“是否甲方 / 乙方原因延期 → 顺延 / 违约金”，每阶段一套 | 没有办法说“这条规则适用于第 2 到第 4 阶段” |
| **“随时可能发生”被画成某一步的分支** | 03 有 10 条带条件的边挂在“服务期开始”“提交服务清单”两个普通步骤上 | 解除权、违约责任在整个服务期内随时可触发，不是某个时点的判断 |
| **旧图的错误被原样继承** | 01 的“是否乙方原因延期 → 否 → 回到需求确认” | 语料是从旧流程的 Mermaid 图反推的（§8 已注明），不是从合同原文抽的 |

合同履行其实是两种东西：一条**履行主线**（里程碑、付款、验收），和一组**或有条款**
（违约、延期责任、解除权）。v1 只有流程图一种语法，只能把后者硬折成前者。
§8 的定稿标准“装得下”检验的是表达力，没有检验表达得对不对、画不画得清。

### 11.2 字段

```json
"rules": [
  { "id": "r-2", "when": "乙方原因导致延期", "then": "乙方支付违约金：每日 0.1%，总额不超 5%",
    "outcome": "negative", "stageIds": ["st-2", "st-3", "st-4"], "sourceIds": ["s-1"] },
  { "id": "r-6", "when": ["乙方连续 3 个月无法满足 80% 用人需求", "乙方未依法签劳动合同被查处"],
    "then": "甲方可单方解除", "outcome": "negative", "stageIds": ["st-1"], "endId": "n-9" }
]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 在规则与节点之间唯一 |
| `when` | ✅ | 触发条件；数组表示“有下列任一” |
| `then` | ✅ | 后果，金额写在这里 |
| `stageIds` | ❌ | 适用的阶段；不写 = 全程。**一条规则覆盖它的所有阶段，不按阶段复制** |
| `outcome` | ❌ | 画法，同节点 |
| `endId` | ❌ | 仅当它导致合同终止：指向那个 `end` 节点 |
| `sourceIds` | ❌ | 依据哪一条款 |

**分界线：** 在某个时点做出、决定流程往哪走的判断（验收通过与否、是否续期）仍是节点加边；
在一段时间内随时可能触发的条款是规则。整改后重新验收这种真实的循环仍是回边。

**校验：** 引用都要存在；`endId` 必须指向 `end`；`when` 不能为空。只由规则到达的终点
没有入边，但不算入口，也不算不可达。**规则 13 不用放宽**：后果都进了规则，剩下的节点
不再有“必须回去”的出边。

### 11.3 呈现

规则画成流程图**下方的一张表**，一行一条：情形（`when`）、后果（`then`）、适用阶段。
分组：每个"规则会导致的终点"一组（"可导致「合同解除」"），其余一组；组内按适用的第一个阶段排，
同阶段按书写顺序。适用范围和结局都**写成文字**，不靠位置去暗示：

- 适用阶段：一个阶段写阶段名，多个写"首 至 尾"，`stageIds` 为空写"全程"；
- 规则会导致的终点右上角标出"条款 N 条"，组头写明这个终点：表和图互相指认，**两者之间不画线**；
- 鼠标移到一行上，它适用的阶段框和它导致的终点一起点亮；点击钉住全文和出处，与节点一致；
- 横排竖排都放在图下方（清单转过来就不好读了）；控制胶囊的"条款"开关关掉整张表。

为什么是表：前两次都更难读。第一次是流程旁一栏卡片，加范围竖条和接到终点的汇总线；第二次是阶段栏下方、
与所覆盖阶段等宽的卡片。两次都让读者去解读几何（卡片的高度、宽度、哪根线通到哪），而条款本来是要逐条读、
互相比较的清单，汇总线还和流程线缠在一起。用同一批规则对比卡片墙，表读得最快。只由规则到达的终点仍排在
它所在阶段的最后一层。
