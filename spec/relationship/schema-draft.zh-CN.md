# relationship · Schema 草案 v0

> 状态：**暂定 v0**（发起人 2026-09 认可为暂用，还不是终稿）。这里的东西还没实现。标 **⚠ 提议** 的是在发起人改动之前一直有效的方案；§7 列出还没回答的问题，以及在回答之前 schema 怎么走。子类在这里不定（第一个子类 `graph` 见 §6.1）。
> 依据：`spec/v0-architecture.zh-CN.md` 的共用约定层（引用一律用 id / 内容元素都有 label / 可选字段宽松）和它 §3 的差异分类（领域语义不同 → 受控枚举，不新增大类）。写法参照 `spec/procedure/schema-draft.zh-CN.md`。
> 范围：关系图 = **某一个时间点上，谁与谁处在什么关系**。随时间发生的事 → `fact`；程序的路径 → `procedure`；规范加事实推出结论 → `justification`。

> **本文写给设计者看。** 写 JSON 的 agent 用另外两样东西：字段表来自 MCP 的 `antu_schema`，机制说明是 `spec/agent/relationship/` 下的一页短文（两者都在 schema 定稿后再写）。

## 0. 决定

发起人已定（2026-09）：

1. **第一版画哪些关系**：四类：**股权与控制**、**合同与债权债务**、**担保与连带责任**、**身份与亲属**（夫妻、父母子女、雇佣、委托代理）。
2. **这张图用来干什么**：案件里"谁与谁、什么关系"的总览，和事实图、程序图配套使用。每条关系都能带出处（合同、登记记录）。它不是尽调用的股权穿透图（那种图的重点是持股比例和层级）。
3. **时间**：一张图是**某一个时间点的截面**。信封里可以写一个可选的 `asOf` 日期；图本身没有时间轴。要看关系怎么变，就画两张图并排比较。

我提议的（**⚠ 提议**，见 §7）：

4. **当事方叫 `entities`，关系叫 `relations`**（各有 `from` / `to`），自由图，和程序图的 `nodes` + `edges` 是同一个思路。`relations` 是业务语言；`edges` 则与程序图字面一致。
5. **每条关系一个 `kind` 枚举**（§4.1），需要专属字段的类别配可选字段（股权的 `share`、债权的 `amount`、担保的 `secures`），而不是一堆自由文本的标签。理由：四类关系读法不同、画法也不同，而专属字段正是校验能查的东西。
6. **`groups`**：读者想框在一起的阵营或一簇（原告方和被告方；一个企业集团）。与事实图的 `groups`、程序图的 `stages` 是同一个思路。
7. **`sources` 原样复用七类来源和结构化定位**（`spec/source-schema-draft.zh-CN.md`）。
8. **没有 `views`。** 和程序图一样，视角是事实图的概念。

## 1. 信封

```jsonc
{
  "specVersion": 1,
  "type": "relationship",
  "title": "张三诉李四 · 当事方及其关系",
  "asOf": "2023-03-10"      // 可选：这些关系成立的日期（ISO 日期）
}
```

写了 `asOf` 时，标签卡上显示"截至 2023-03-10"。除此之外它不改变任何东西。

## 3. 字段规则

### 图级字段

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `asOf` | ❌ | ISO 日期字符串 | 这些关系成立的日期，写在信封里 |
| `groups` | ❌ | object[] | `{ id, label }`，见 §4.3 |
| `entities` | ✅ | object[] | 当事方，见下 |
| `relations` | ✅ | object[] | 当事方之间的关系，见下 |
| `sources` | ❌ | object[] | 图内的来源表；七类与定位字段完全复用事实图 |

### `entities[]` 的每一项

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | ✅ | string | 图内唯一，被 `relations` 引用 |
| `kind` | ✅ | string 枚举 | `person` / `company` / `organization` / `government` / `other`，见 §4.2 |
| `label` | ✅ | string | 显示在当事方上的名字 |
| `role` | ❌ | string | 在本案中的角色（"出借人"、"保证人"），名字下面的一行短字 |
| `detail` | ❌ | string | 注册资本、证件号等放不进框里的细节；全文在浮层里 |
| `groupId` | ❌ | string | 引用 `groups` 里的 id |
| `sourceIds` | ❌ | string[] | 引用本图 `sources` 里的 id |

### `relations[]` 的每一项

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | ✅ | string | 关系之间唯一（`secures` 会引用它） |
| `from` | ✅ | string | 某个当事方的 id；**关系的方向从这里出发**，见 §4.1 |
| `to` | ✅ | string | 某个当事方的 id |
| `kind` | ✅ | string 枚举 | 见 §4.1 |
| `label` | ❌ | string | 线上的一句短话。省略时渲染器按 `kind` 和专属字段补一个（"持股 60%"） |
| `detail` | ❌ | string | 条款、日期、全文；在浮层里 |
| `directed` | ❌ | boolean | 覆盖这一类的默认方向，见 §4.1 |
| `share` | ❌ | number（0–100） | **仅 `equity`**：持股百分比 |
| `amount` | ❌ | string | **`debt` 和 `contract`**：金额，写成读的样子（"人民币 50 万元"） |
| `secures` | ❌ | string | **仅 `guarantee`**：这笔担保所担保的那条关系的 id |
| `sourceIds` | ❌ | string[] | 引用本图 `sources` 里的 id |

`amount` 特意用字符串：它是拿来显示的，不是拿来算的，币种或者区间（"约 50 万元"）也塞不进数字。

## 4. 机制

### 4.1 关系类型（`kind`）与方向  **⚠ 提议**

| `kind` | 含义 | 方向 `from → to` | 默认 | 专属字段 |
|---|---|---|---|---|
| `equity` | 持有股权 / 出资 | 持有人 → 被持有的主体 | 有向 | `share` |
| `control` | 不靠持股的实际控制、一致行动、委派 | 控制方 → 被控制方 | 有向 | |
| `contract` | 当事方之间的合同（买卖、租赁、服务……） | 两个方向都行（要紧的话，付款方或要约方写在前） | **无向** | `amount` |
| `debt` | 债权与债务 | **债权人 → 债务人** | 有向 | `amount` |
| `guarantee` | 保证、抵押、质押或连带责任 | **担保人 → 债权人** | 有向 | `secures` |
| `kinship` | 夫妻、父母子女、兄弟姐妹、继承人 | 两个方向都行 | **无向** | |
| `employment` | 用人单位与劳动者 | 用人单位 → 劳动者 | 有向 | |
| `agency` | 授权、代理 | 委托人 → 受托人 | 有向 | |
| `other` | 其他 | | 有向 | |

- `directed` 覆盖默认（父母指向子女的 `kinship` 可以写 `directed: true`）。
- 方向规则每类一句话，写进给 agent 的机制说明；这个枚举小到 agent 记得住。
- 一笔 `debt` 和它所出自的 `contract` 是同一对当事方上的两条关系。这是有意的：合同说约定了什么，债权说谁欠谁。

### 4.2 当事方类型（`kind`）

`person`（自然人）、`company`（法人企业）、`organization`（合伙企业、事业单位、社会组织、非法人组织）、`government`（行政或司法机关）、`other`（比如没有名字的一群人，如"讨债方"）。

类型只决定框的形状和颜色，本身没有法律含义。

### 4.3 分组（`groups`）

分组是围在若干当事方外面、带标签的框，当事方用 `groupId` 说明自己属于哪一组（原告方和被告方；一个企业集团）。一个当事方最多在一个分组里，分组不嵌套。分组是可选的，没写 `groupId` 的当事方站在所有框外面。

### 4.4 担保指向它所担保的债权（`secures`）

一笔担保担保的是**某一笔具体的债权**，不是债务人这个人。`secures` 写明那一笔（一条 `debt` 或 `contract` 关系），于是担保既从担保人画向债权人，**又**明显地挂在那条债权上。没有它，读者分不清一笔担保是给两笔借款中的哪一笔的。

### 4.5 来源（`sources`）与"没有视角"

当事方和关系通过 `sourceIds` 引用来源；来源表是每张图都带的那一张（`spec/source-schema-draft.zh-CN.md`）。没有 `views`：它是事实图的概念。

## 5. 校验规则  **⚠ 提议**

错误逐条报，带字段路径和 id，风格与事实图、程序图一致：

| # | 规则 | 结果 |
|---|---|---|
| 1 | `entities` 和 `relations` 是非空数组 | 报错 |
| 2 | `id` 必填，且在 `entities` 内、`relations` 内各自唯一 | 报错 |
| 3 | `entity.kind` 和 `relation.kind` 在各自的枚举内 | 报错 |
| 4 | 每个当事方都有非空的 `label` | 报错 |
| 5 | `from`、`to` 指向存在的当事方 | 报错 |
| 6 | 不许自己对自己的关系（`from === to`） | 报错 |
| 7 | 不许重复的关系（`from`、`to`、`kind`、`label` 都相同） | 报错 |
| 8 | `groupId`、`sourceIds` 指向存在的 id | 报错 |
| 9 | `share` 是 0–100 的数字，且只出现在 `equity` 上 | 报错 |
| 10 | `amount` 只出现在 `debt` 和 `contract` 上 | 报错 |
| 11 | `secures` 只出现在 `guarantee` 上，且指向一条存在的 `debt` 或 `contract` 关系 | 报错 |
| 12 | 写了 `asOf` 时必须是 ISO 日期 | 报错 |
| 13 | 指向同一个主体的 `equity` 的 `share` 加起来超过 100 | **提示**，不报错（可能是数据错了，也可能是来源里就错了） |
| 14 | 一个当事方没有任何关系 | **提示**（它会漂在图旁边） |
| 15 | 一笔 `guarantee` 没有写 `secures` | **提示**（它担保的是哪一笔？） |
| 16 | 股权成环（交叉持股） | **提示**，允许（现实里存在） |

结构错误会挡住绘制，提示不会。与程序图同一个分法（`spec/procedure/schema-draft.zh-CN.md` §5、§6.3）。

## 6. 呈现（渲染器的事）  **⚠ 提议**

### 6.1 第一个子类：`graph`

- **排布：阵营并排，行由所有阵营共用。** 一个分组是一个阵营，阵营并排站着（争议双方隔一条通道面对面）；不属于任何分组的当事方，两个阵营时站在中间不画框，其他情况排在最后。每个当事方所在的层，先在整张图上算一次，不管阵营（ELK 的分层算法），于是持股人在被持股主体之上、债权人在债务人之上、担保人在债权人之上，**不论各自在哪个阵营**，同一层的两个当事方之间跨通道的线可以直着走。然后每个阵营各自排一遍，决定它的成员怎么并排。（一开始试过把框做成 ELK 的复合节点，成员在不同层的阵营会被打散；在例子上量过，债权人被夹在了债务人阵营的两半中间。）横排是同一张图的转置。
- **连线**：用和程序图跨阶段连线同一个正交寻路（`flow/router.js`）：折数最少、其次最短，避开每个当事方和分组标题，进目标前有一段直线。这里交叉的代价比流程图低（大约一个折的分量），所以线不会为躲一次交叉绕整张图一圈。默认曲线，可选折线。第三种图用上时，这些文件再搬到共用的位置。
- **标签**：先走线，后放标签，每个标签放在自己那条线旁边、避开其他一切；拥挤的通道里找不到空位时，放在它自己的线上（标签的底色盖住下面那一段线）。
- **关系的样子**随类型：颜色和线型按类型分（`equity` 蓝、`debt` 红、`guarantee` 紫色虚线、`kinship` 双线、`contract` 灰、`control` 粗线），有向才画箭头，类型名作为默认标签，跟随界面语言。
- **担保和它担保的债权**：写了 `secures`、且两条线离得近时，从担保线的中间到债权那条线画一小段点线接上。离得远就不画（一条长长的斜线，说得比花掉的少）；这一对关系在当事方的浮层里总是能看到。
- **悬停和点击**与别处一致：悬停当事方时点亮它、淡出不碰它的关系，浮层里列出它和谁有什么关系；点击钉住浮层，里面有 `detail` 和来源。看一个当事方从不移动视图。

### 6.2 控制胶囊

| 控件 | 形态 | 说明 |
|---|---|---|
| 方向 | 分段 | 竖向 / 横向 |
| 连线样式 | 分段 | 曲线（默认）/ 折线 |
| 类型 | 开关 | 数据里用到的每一类关系一个：显示 / 隐藏这一类关系。这是关系图对事实图"视角"的回答：同一份数据，一次看一类 |
| 关系标签 | 开关 | 显示 / 隐藏线上的标签 |
| 分组框 | 开关 | 写了 `groups` 时可用 |
| 导出图片 | 动作 | 复用共用的导出 |

记住什么，沿用程序图的规则（那边的 §6.2）：方向和开关按图记住，连线样式对所有图记一次。

### 6.3 规模

一个案件的截面，当事方不多，通常 4 到 15 个。超过大约 25 个当事方时给一条提示（和程序图对层数的做法一样），不算错误。

## 7. 还没回答的问题，以及暂时怎么走

发起人还没回答这些问题。**在某一条被回答之前，下面写的默认值就是要做的。** 改默认值动的是 schema 和校验，不动排布和渲染器。

1. **命名。** `entities` / `relations`（我的提议）还是 `entities` / `edges`（与程序图用同样的词）？只是用词不同。 **暂时：** `entities` / `relations`。
2. **类型枚举。** 九类（§4.1）还是更少？可以合并的候选：`control` 并进 `equity`，`employment` 和 `agency` 合成一个 `authority`。类型多，读起来清楚；类型少，模型更容易选。 **暂时：** 用 §4.1 的九类。
3. **无向关系。** `contract` 和 `kinship` 默认不画箭头。这样对吗？还是合同应该总是标出谁是要约方？ **暂时：** 这两类不画箭头。
4. **专属字段。** v1 只有 `share`、`amount`、`secures`？想得到的还有 `guaranteeMode`（保证 / 抵押 / 质押）、`since`（关系开始的时间）。时间那条决定（§0.3）说不做，但只在浮层里显示的一个 `since` 日期成本很低。 **暂时：** 只有这三个。
5. **分组。** 一个当事方能不能同时在几个分组里（一个人既在家庭一方，又在公司一方）？画出来框不能重叠，所以我写的是不行。 **暂时：** 一个当事方最多在一个分组里。
6. **第一批语料。** 我提议把已有事实图示例（于欢案、张娟诉彭宇、快播案）里的当事方改写成关系图，再从零写一份股权结构和一份担保案，就像程序图用七份合同验证那样。你有更想用的真实案件吗？ **暂时：** 三份事实图案件，加一份股权结构、一份担保案。

## 8. 本轮不做

- 随时间变化的关系（每条关系有起止日期、按日期筛选）；
- 冲突来源的对比展示（质证），它在证成图这一族里扩展；
- 把金额当数字（加总、合计、一致性检查）；
- 编辑；
- 第二个子类（矩阵或关系表）。

## 9. 与另外两类的比较

| | 事实图 | 程序图 | 关系图 |
|---|---|---|---|
| 结构 | 车道上的时间点和事件 | 节点和边的自由图 | 当事方和关系的自由图 |
| 时间 | 轴 | 流程 | 一个 `asOf` 日期 |
| 分组 | `groups`（分侧） | `stages`（分栏） | `groups`（分框） |
| 视角 | 有 | 没有 | 没有，改用类型筛选 |
| 专属字段 | 日期 | `condition`、`main` | `share`、`amount`、`secures` |
| 排布 | 自己的网格 | 每个阶段 ELK + 寻路 | ELK 分层 + 寻路 |
